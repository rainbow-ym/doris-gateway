# Doris 安全网关业务与架构自查

日期：2026-10-15（北京时间）。对象：当前本地源码及 132 构建的 accounts.1 / worker h2fix1 代码。

## 结论与证据等级

当前实现是限定场景的工程试用版本，不能据现有证据认定为生产级通用数据安全网关。“所有复杂 SQL 精确血缘”“与 Doris 事务保持一致”“一个查询周期内无遗漏同步”“任意规模多用户可用”均不能作为当前承诺。H2 启动修复解决的是一个运行问题，不解决下面的业务一致性问题。换 MySQL 本身也不能修复这些问题。

- **实测**：本次 AuditProbe.java 在独立内存 H2 中执行当前已编译类；不访问 Doris，不读取生产凭据。
- **静态确认**：实现和调用链直接可见；影响按条件描述，未对生产系统实施利用或并发故障注入。
- **待专项验证**：还需要端到端、并发、重启、断网、事务测试，不能报告为已发生的数据泄露。
- P0 表示应优先阻断的保护连续性风险，P1 为重要正确性/一致性问题，P2 为可维护性与工程化不足；不是 CVSS 评分。

## 一、优先处理的保护与业务正确性问题

### F01 / P0：系统库豁免条件可误命中业务 SQL（实测）

ManagedSqlExecutionService.statementType 第 341 行以 normalized.contains("INFORMATION_SCHEMA.") 判定整条语句 BYPASS，不检查 AST 中实际访问对象。因此 SELECT 字符串、CTAS 的 WHERE 字符串含该内容也会跳过 managed-object prepare 验证和变更登记。

实测：`SELECT 'information_schema.' AS note FROM secret_table` 返回 BYPASS；`CREATE TABLE copied AS SELECT secret FROM src WHERE 'information_schema.' <> ''` 也返回 BYPASS。

这不是用户接受的 SHOW/information_schema 不过滤：用户接受的是元数据可见性差异，不是业务 SQL 整体绕过纳管。此处不自动证明普通 SELECT 绕过结果脱敏，但已经证明对象登记/检查的放行边界错误。

建议：用 AST 按实际对象判定，仅豁免纯元数据语句；混合系统表与业务表的语句仍走业务保护。常量与注释不应影响豁免。

### F02 / P0：CTAS 标量子查询来源遗漏（实测）

SqlLineageAnalyzer.resolvePlain 第 160 行后的表达式 visitor 只收集 Column，没有为 SELECT 表达式中的 SubSelect 建立独立作用域。

实测：`CREATE TABLE scalar_copy AS SELECT (SELECT secret FROM src LIMIT 1) AS innocent` 未被拒绝，得到 0 条 edges。已有 src.secret 的确认标签也不能弥补没有来源边的问题。

ManagedSqlExecutionService.validateReferences 对 CREATE 主要依赖 analysis.edges 收集来源。遗漏来源同时影响纳管来源验证及目标继承。若整个 Proxy/Doris 路径接受该 SQL，目标别名又不命中字段识别规则，就存在未继承保护的风险；本次未在真实 Doris 执行该 SQL。

建议：未解析表达式必须显式 UNKNOWN 并拒绝，不得用“零来源”代替“纯常量”；增加标量子查询、相关子查询、CTE 列表、集合操作、窗口表达式和 Doris 特殊语法的负向测试。

### F03 / P0：策略发布有无规则窗口，查询快照不完整（静态确认；泄露待并发验证）

DistSqlService.statements 第 220 行附近更新已有规则时使用 DROP MASK RULE 后 CREATE MASK RULE，execute 逐条执行。AdminController.publish 直接调用 publish，没有统一冻结相关对象，也没有按逻辑库版本互斥。

UserOutputPlan 对未匹配用户例外的字段返回 DEFAULT；MaskMergedResult.findMaskAlgorithm 第 167 行起回退读取 Proxy 当前规则，不存在时返回 Optional.empty，getValue 返回原值。用户规则快照并没有包含固定的全局算法决策，且每个结果单元格重新找规则。

因此代码上存在发布中途规则缺失或不同版本混用的路径。需用并发查询/失败注入验证端到端影响，不应因测试单次查询成功就否认风险。

建议：先编译完整不可变策略版本，再原子切换；每次查询固定版本，结果列提前编译动作。最小过渡方案是发布期间拒绝相关新查询，并对已开始查询保留旧规则实例；失败保持关闭，不能返回无保护结果。

### F04 / P1：替换已有视图被当成 NOOP（实测）

ManagedSqlExecutionService.prepare 第 82 行起，只要 isCreate 且目标已 ACTIVE，就记录 NOOP，不区分 IF NOT EXISTS 与 CREATE OR REPLACE VIEW。commit 对 NOOP 不更新元数据或策略。

实测：`CREATE OR REPLACE VIEW v AS SELECT secret AS innocent FROM src` 的 prepare 返回 NOOP。该分支不能代表 Doris 真正没有修改视图。

建议：AST 区分新建、条件不变、替换；替换视图必须冻结、重新分析、刷新和发布。

### F05 / P1：schema 同步不是完整差量，列顺序可能错误（静态确认）

AdminStore.upsertColumn 第 163 行起只插入/更新，scanTable 没有清理已消失 metadata_columns；tableColumns 第 440 行附近按 id 而非物理 ordinal_position 取列。SqlLineageAnalyzer 的 SELECT * 和未指定目标列的 INSERT SELECT 使用它。

新增列插到中间、删除或重命名后，metadata_columns 和 managed_columns 可不一致；血缘按历史 ID 对齐，可能出现错误继承或发布引用旧字段。ALTER 分支也没有专门继承字段重命名的旧标签。

建议：事务化保存 schema snapshot，使用物理列序与稳定对象版本；对 DROP/RENAME/REORDER 显式处理，未知变更拒绝恢复 ACTIVE。

### F06 / P1：继承会覆盖已有目标策略，缺少保护强度合并（静态确认）

AdminStore.inheritPolicy 第 451 行起直接覆盖 assigned_policy。edgeRows 仅检测本次 SQL 多来源之间的不同策略，不与目标原有策略比较。向一个已有更严格策略的目标列 INSERT SELECT，可能改为源字段的另一种策略。

建议：敏感类型、保护等级、输出动作分离；继承执行确定的合并/冲突规则，不能把后一次写入当成覆盖理由。管理员显式降级需要独立记录与确认。

### F07 / P1：用户级 AES 返回规则缺参数（静态确认＋目录实测）

PolicyCatalog 的 OUTPUT_AES_GCM props 为空。DistSqlService.desired 会补 key-env/key-id/aad，但 UserOutputPlan 第 55 行起直接使用 catalog props 初始化算法，没有相同补充。OutputAesGcmMaskAlgorithm.init 要求 key-env 和 key-id。

因此“全局 AES 发布”和“用户 MASK + AES”不是同一条完整配置路径，后者会因必要参数缺失而失败。这里主要是功能不可用，不是已确认明文回退。

建议：统一算法配置编译器，在保存时验证密钥引用；AAD、keyId、密钥轮换策略独立于 UI 和 DistSQL。

### F08 / P1：短值可能完全不脱敏（静态确认）

CodePointMasking.keepFirstLast 在保留长度之和大于等于原长度时返回原文。当前电话规则保留 3+4，地址保留 6+0，所以短电话、短地址原样返回。这是现有算法行为，是否违反要求需明确业务规则，不能把“配置了脱敏”解释为所有值都会变化。

建议：增加短值策略（全部隐藏/保留首字/拒绝），并给 UI 展示空值、短值、超长值、Unicode 的示例。

## 二、事务、恢复与状态管理

### F09 / P1：血缘事件与边非原子，失败重试会永久缺边（实测）

AdminStore.saveLineageEvent 第 472 行起先写事件再写 edges，没有本地事务；重试若 event_id 已存在则直接返回 false。

实测在独立 H2 用过长 sourceColumn 诱发边插入失败后，事件头仍存在；重试返回 false，边数仍为 0。

建议：事件头和边放入一个事务；事件应有完成状态与唯一边约束，重试补齐或整次回滚，不能仅按事件头去重。

### F10 / P1：业务成功回调不是 Doris 事务提交（静态确认）

GatewaySQLExecutionHook.finishSuccess 触发管理侧 commit，它是语句执行回调，并非以真实事务 ID 关联数据库 COMMIT/ROLLBACK。多语句显式事务、回滚、连接中断、已经执行但回包失败不能由此证明一致。

ManagedSqlExecutionService 的 PREPARED/SYNCING/FAILED 状态跨多条自动提交的 JdbcTemplate 更新，无一个本地事务覆盖状态与任务落库。Java synchronized 只能串行同一个对象实例，既不覆盖 Doris 的实际执行区间，也不是分布式事务。

建议：当前先明确支持 autocommit 的语句边界；未验证的显式事务变更拒绝。把真实执行状态、保护发布状态和客户端确认状态拆开，采用本地事务与 durable outbox；未知结果不能假装事务已完成。

### F11 / P1：恢复缺少结果证据与对象代次（静态确认）

pendingManagedExecutions 包含 PREPARED/SYNCING/FAILED；ManagedRegistryReconciler 超时后调用 reconcile → commit。CREATE 看见同名表、DROP 看不见表，不能证明是本次操作造成；INSERT SELECT/UPDATE 的恢复没有验证原写入是否成功，就继承并恢复 ACTIVE。

对象按连接 ID、库、表名识别，没有 generation；同名删除重建、并发 CREATE、外部建表可能使旧任务影响新对象。prepare 的 CREATE 对非 ACTIVE 对象可再次 upsert 并覆盖 pending_execution_id。

建议：引入 executionId 关联的 CAS 状态转换、对象代次和 schema 指纹校验；UNKNOWN 与“执行成功但待同步”分开。无法确认结果时显式人工核实，不能只按超时推定成功。

### F12 / P1：回滚只回滚 Proxy 规则，不回滚配置事实源（静态确认）

DistSqlService.rollback 第 161 行起更新 Proxy 与版本日志，没有回滚 metadata_columns 的 assigned_policy。下一次 publish/DDL 发布可能再次应用旧 desired。用户级策略类型匹配则仍读管理库字段标签。

建议：定义 desired/applied/active 三种版本，回滚生成新的完整目标版本；UI 明确“未发布”和“已生效”，不能把两套状态混为当前策略。

### F13 / P1：执行成功后审计失败可能把业务成功表现为失败（静态确认）

StandardDatabaseProxyConnector.execute 在 executeWithIdentity 返回后同步调用 auditExecution(EXECUTED)，异常会使请求失败。Doris 可能已完成写入，客户端若自动重试可重复执行。审计 FAIL_CLOSED 的目标合理，但没有区分执行前拒绝与执行后结果不确定。

建议：执行前确保审计可落盘；执行后以本地持久事件重试，不重放业务 SQL。向客户端给出明确的“已执行、确认失败/勿重试”类别及请求 ID。

## 三、耦合与扩展性

### F14 / P1：管理面与业务请求强同步耦合（静态确认）

查询路径包含账号检查/凭据获取、prepare、用户策略、审计及结果血缘等同步 HTTP。worker 或其 H2 故障不仅影响页面，还会影响业务查询。prepare/commit 为同一个服务对象上的 synchronized，commit 内含元数据查询、规则发布和用户映射，慢 DDL 会阻塞其它请求进入 prepare。

建议：不必立即拆微服务。先在同一进程内拆分查询决策服务与后台任务；按对象/库锁定，策略用有版本的本地快照。保留失效时关闭访问，不能为了性能变成忽略保护。

### F15 / P1：结果逐单元格全表扫描策略，连接池硬上限（静态确认）

UserOutputPlan.decision 每次遍历整个逻辑库的 columns 和 rules；MaskMergedResult.getValue 每个单元格调用它。近似成本为返回行数 × 返回列数 ×（库字段数＋规则数），而不是仅查询涉及字段数。

UserBackendConnections 池键包含 connectionId、库 URL、用户名、凭据版本，最多 256 个池，每池最多 8 个连接。Hikari 空闲连接回收不会移除 POOLS 的键，只有观察到账号 epoch 变化才清部分池。多库多用户/重复连接/凭据变更可耗尽池数量，不等于支持 256 个用户。

建议：每次查询一次性编译 result-column → action/algorithm；维护索引、版本缓存、明确总连接预算、池 LRU/TTL 淘汰和指标，再实测负载。

### F16 / P1：物理对象身份与维护连接账号未解耦（静态确认）

managed_objects、metadata_columns 以 connection_id 作为物理对象身份组成部分；logical_databases 指向维护连接。该账号改密、退役会牵动共享元数据；AccountLifecycleService 对有依赖的维护连接直接禁止删除/改密，缺少维护身份迁移流程。

集群物理端点等价性用 host 字符串＋port 判断，不同 FE、VIP 与直连 IP 可能被当成不同集群。一个 worker 的实际集群边界依靠部署/接入约束，不是独立 canonical cluster identity。

建议：稳定的集群/对象 ID 与凭据 ID 分离；一个集群可有多个 FE 访问端点及轮换凭据。保留现在每集群独立 worker/Proxy 的隔离，不要为“统一”贸然共用运行时。

### F17 / P2：内核同名类覆盖与多套 SQL 解析器强耦合（静态确认）

src/main/java/org/apache/shardingsphere 下覆盖了解析、连接、结果合并、权限检查和持久化等多处内部类；UserBackendConnections 反射访问 5.5.3 ConnectionIdGenerator。控制面又使用 JSQLParser、正则、独立注释处理；AccountCommand/DorisTableProperties 在模块间有重复实现。

建议：固定内核版本与兼容性测试；把覆盖集中到适配模块，把公共 SQL/账户协议抽到共享模块。不能把升级 ShardingSphere 当普通依赖升级。优先缩小覆盖面，而非现在重写代理。

### F18 / P2：敏感类型、识别规则、输出算法未完全分离（静态确认）

PolicyCatalog 在 Java 中写死类型、算法、参数和默认字段名；FieldMappingRules 的 sensitive_type 实际指向这些 ID；用户规则按 assignedPolicy 匹配“敏感类型”。同一个类型换另一种展示算法时，会影响类型识别语义。UI 新增映射规则不等于可新增任意策略模板。

建议：拆 sensitive_type、recognition_rule、mask_template、user_output_policy、policy_version；先支持已有四类的参数化和版本化，不无限扩展为脚本执行引擎。

## 四、运维、安全与验收缺口

### F19 / P1：安全保护边界不是“所有敏感数据自动保护”（静态确认/设计限制）

未匹配识别规则、未确认策略的普通字段仍可返回原文；这不等同于“未知表拒绝”所保护的对象级边界。字段名或注释识别不是内容识别。外部直接 CREATE/ALTER 在扫描前也不会被所有场景即时感知。

同理，单纯返回脱敏不阻止通过 WHERE/COUNT/布尔条件逐步推断敏感值。需求允许明文匹配时必须明确这种边界；不要求本轮扩展为反推断系统。

建议：接入向导显示覆盖率、未分类字段和管理员确认；对高敏源设置“未分类不允许发布”可选门禁。明确外部 DDL 的扫描/确认窗口。

### F20 / P1：审计、凭据与通信仍需生产加固（静态确认）

AccountAccessService.url 等硬编码 useSSL=false；门户默认 HTTP。worker 内部 token 接口可返回真实用户密码，默认 loopback 降低暴露，但需要严格限制管理端口。平台管理员有 CSRF、BCrypt、登录节流、会话控制；不能据此认为数据库链路也有 TLS。

managed_sql_executions 保存 raw_sql，可能含敏感字面值；管理审计 audit_log 只有 action/detail/time，无统一操作者/traceId。未发现审计与血缘历史的保留清理任务，LIMIT 仅限制展示，不限制增长。主密钥在 env，缺少在线轮换、版本与灾难恢复演练。

建议：可配置 TLS、密钥引用和轮换；SQL 原文最小化/受控加密；审计关联 actor/queryId/executionId/policyVersion，设保留与归档。不要记录或公开真实凭据。

### F21 / P2：健康检查、版本、安装与升级闭环不足（静态确认＋此前验证）

Docker 管理服务健康检查主要看 TCP 端口；/api/health 固定 UP 不能验证控制凭据、规则发布、权限映射及 Doris。h2fix1 镜像内部健康接口仍报告 accounts.1，前端也存在单独写死版本，难准确核对。

初始化配置和版本需要人管理；启动中途失败没有完整阶段恢复。修复脚本会保留停止的旧容器，这是可恢复性而不是完整回滚系统；也不能等价承诺整个数据库的冷备。镜像依赖运行时、主机网络、磁盘和系统调用兼容，不能承诺不依赖外部环境。

建议：区分存活/就绪/业务自检；内嵌构建 ID、镜像 digest、schema 版本；一键预检、逐步状态、更新前一致性备份、可验证回滚。保留旧 Docker 无 Compose 的要求，不必引入容器编排。

### F22 / P1：权限同步是有限实现，不是全生命周期完整镜像（静态确认）

账号管理限制 root、默认 Host/%、有限语法，不覆盖完整角色、外部认证、全部 Host 匹配与复杂授权。直连 Doris 创建用户不能凭空获得明文密码，现有周期 refreshAll 刷新已关联账户的授权快照，不等于自动注册所有新用户。

撤权、改密有 epoch 失效机制，这是正确方向；但使用全局连接 ID 截断会让某些有效新连接也需要重连。外部改密和已有物理连接的有效期需专项验证。权限快照 UNKNOWN/ALLOWED 不能替代真实 Doris 执行权限；代码目前仍使用真实业务身份执行，这是应保留的基础。

建议：明确生命周期支持矩阵；默认凭据受控导入或网关捕获，外部变更采用可解释的刷新与阻断策略；会话 epoch 记录在认证时，而不是用全局 ID 粗略截断。

## 推荐整改顺序与验收
