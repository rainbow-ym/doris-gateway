# 审计补投持久化、对象代次和旧任务隔离

日期：2026-10-17（北京时间）。本批仅开发和 132 隔离测试，未发布到正式服务或离线安装包。

## 一、审计补投

沿用 Proxy 挂载日志目录，默认队列目录 `/opt/gateway/logs/audit-outbox`，可通过 `GATEWAY_AUDIT_OUTBOX_DIR` 指定专用持久目录。

- 每条审计消息先写临时文件、强制刷盘、原子改名，再发送。目录和文件在 Linux 分别限制为 0700/0600。
- STARTED 必须得到管理端确认，之后才能执行原业务语句。
- EXECUTED / UNKNOWN 投递失败保留队列文件，仍向客户端返回上一批的待核实错误；后台只补投审计，不执行任何业务 SQL。
- 网关启动入口 `GatewayBootstrap` 主动启动补投线程，不需要等第一次业务请求。每 10 秒尝试补投，单批最多 32 条，遇到失败暂停至下一轮。
- worker 新增 `audit_receipts`，按请求编号及状态幂等接收；去重凭据和 audit_log 在同一本地事务中写入。同编号不同内容拒绝覆盖。
- 单消息上限 16 KiB、目录条目上限 10000；超限或持久化失败保持拒绝执行，不丢弃消息腾空间。

队列只含用户、库、SQL 摘要、请求编号和执行状态，不含业务 SQL 或返回结果。包含用户标识，仍属于受控运维数据。残留 `.tmp` 文件不自动投递、不自动清理；不可把它当成完整消息。

## 二、对象代次与持久化恢复任务

复用现有 `managed_sql_executions` 作为持久化恢复任务，不引入消息中间件。

| 位置 | 新字段 | 用途 |
| --- | --- | --- |
| managed_objects | generation_id | 网关管理的对象代次，预留新建对象时生成 UUID |
| managed_sql_executions | target_generation、rename_generation | 固定任务针对的目标及改名预留对象代次 |
| managed_sql_executions | success_received | 已收到 Proxy 执行成功回调的持久证据 |
| managed_sql_executions | recovery_attempts | 同步尝试次数，防止无限重试 |

对象预留和任务记录放在同一个本地事务中，写任务失败会撤销预留。对象有 pending_execution_id 时，其他创建、重新初始化或扫描不得覆盖其归属。

恢复前核对对象代次及 pending_execution_id。失配时仅将旧任务标为 `STALE_EXECUTION`（界面显示“旧任务已隔离”），不按旧表名重建或修改当前对象。没有 success_received 的任务转 UNKNOWN，不能仅凭表存在就恢复成功。

成功回调先持久化 receipt，再执行元数据与保护同步。同步失败保留任务，重启后仍可重试同步，但不重新执行原始 SQL。累计 10 次同步尝试（包含首次）后进入 `MANUAL_REQUIRED`，保持阻断并停止自动重试。

对象开放、任务 COMMITTED 与用户权限投影在本地事务中完成；权限投影失败会回滚本地完成状态。失败处理只操作仍由任务拥有的对象，不再因旧表名消失而 upsert 一个对象。

## 三、升级注意事项

- 增加字段使用兼容性建列；已有对象补发网关代次。历史任务不伪造 success_received，也不自动猜测旧任务属于哪一代对象。
- 必须配套更新 Proxy、启动脚本和 worker。仅替换 jar 而继续使用旧启动入口，会失去“无业务请求时主动补投”的保证。
- 本批测试启动镜像使用 `docker/Dockerfile.outbox`，依赖测试基础镜像，尚不是可交付的独立构建清单。
- 队列目录应随 Proxy 日志卷备份；不要同时启动两个 Proxy 共用同一补投目录。

## 四、验证

最终完整测试：admin 97 项，96 通过、1 跳过；Proxy 61 项，37 通过、24 跳过。实际执行共 133 项通过，25 项跳过。

新增单元验证包括：预留/任务原子性、占用对象不可抢占、同名新代次与旧任务隔离、无成功回执禁止恢复、成功回执跨重新初始化保留、重试上限、权限投影失败回滚、审计幂等及审计失败事务回滚、补投文件跨对象重建恢复、冲突消息与超限拒绝。

真实隔离演练：

1. 网关 CREATE → DROP → 同名 CREATE。停止隔离服务，在其 H2 冷库将旧代次任务改为待重试；重启并调用恢复接口。旧任务被隔离，新对象状态完全未变，查询继续脱敏，最后删除合成测试表。
2. 停止隔离 Proxy，向其持久目录注入未投递消息及“已落库但确认丢失”消息。启动 Proxy，不发送业务查询，验证后台主动补投；管理端每条消息只有一条审计，队列消息清除。
3. 回归自动血缘隔离 6 组、事务门禁 3 组、保护边界 6 组、多用户 13 组、策略快照 4 组、中文接入 3 组、中文账号生命周期 6 组，以及审计请求编号关联。

审计空闲重启测试首次暴露启动延迟问题，修正为 GatewayBootstrap 后复测通过。上述文件注入模拟持久化后中断，不是生产断电或文件系统损坏测试。

**未关闭的验证异常：**一次完整构建中的已有并发版本审计测试出现 H2 2.1.214 `audit_log` 自增主键冲突。后续完整测试通过，该专项连续 5 次重跑也通过；没有修改测试以规避，也没有定位其根因。不能据复跑通过就认定问题消失，这是正式发布前需要继续排查的风险。

## 五、边界与未完成项

- generation_id 是网关代次，不是 Doris 原生表 ID。绕过网关的同名、同结构删表重建，当前不能自动准确识别；需要物理对象证据或外部 DDL 审计。
- 未实现跨 Doris、Proxy、H2 的分布式事务，也不支持多个 worker 共写一个系统库。
- 部分 RENAME 元数据步骤完成后若后续发布失败，恢复可能因旧名称归属不再成立而隔离任务并保持新名称阻断。当前选择停止猜测，不声称所有改名中断均能自动恢复；后续需显式阶段日志和人工核实入口。
- MANUAL_REQUIRED、UNKNOWN 和旧代次任务不会自动变为 ACTIVE。当前提供中文原因，不提供无证据“强制成功”按钮。
- 审计去重表与历史记录尚无归档/保留清理，队列也未做吞吐或大规模压力验收。共享同步补投路径的延迟需后续评估。
- SQL 请求编号、managed executionId、Doris queryId 尚未完全贯通；补投不等于自动证明业务提交结果。
