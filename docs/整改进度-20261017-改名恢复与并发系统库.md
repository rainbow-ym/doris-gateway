# 改名中断恢复与系统库并发写入

本批继续最小范围开发，仅更新 132 的隔离测试实例（3312 / 18086），没有更新正式服务或重新导出安装包。

## 1. 改名恢复

复用持久化执行任务，增加两个字段：

| 字段 | 含义 |
| --- | --- |
| rename_registry_applied | 元数据登记已经迁移到新名称 |
| rename_policy_version | 改名对应的已校验、生效策略版本 |

登记迁移与第一个标记在同一个系统库事务中提交。策略快照激活与第二个标记也在同一个系统库事务中提交。重试根据标记继续剩余同步，不重放 Doris SQL，也不会再次将同一策略从旧名搬到新名。

恢复仍校验 generation_id、pending_execution_id 和策略版本。旧名称已经被新对象复用、目标归属变化、或已有后续策略版本时，保持阻断并要求核实，不覆盖新对象或后续策略。改名前后的两个对象状态、用户权限投影仍由既有完成事务收口。

不推断历史任务的缺失阶段标记；旧版本已经中断且缺少证据的任务仍可能需要人工处理。没有引入跨 Doris、Proxy、系统库的分布式事务。

## 2. H2 并发自增冲突

之前偶发的自增主键冲突与 H2 MySQL 兼容模式已知的并发序列更新缺陷相符。上游依据：[问题 3950](https://github.com/h2database/h2database/issues/3950)、[修复 3951](https://github.com/h2database/h2database/pull/3951)。不能仅凭后续复跑成功推断原问题已经自然消失。

本批没有替换 H2 引擎或内部类：worker 的系统库连接在创建连接池之前统一将旧 URL 中的 MODE=MySQL 转为 MODE=REGULAR，新默认配置亦使用 REGULAR。旧环境变量覆盖也经过此处理，仍使用原数据库文件和数据。

8 个线程通过真实 Hikari 连接池累计插入 16,000 行，检查实际数据库模式和行数，测试通过。完整 worker 测试及真实旧数据启动、策略发布、权限映射均通过。原竞争问题没有在本批稳定重现，因此不将压力测试通过等同于对所有并发故障的证明。

范围仅为 worker 系统库；platform 和 ShardingSphere 自身存储配置未在本批变更，不能据此宣布所有 H2 使用位置均已完成治理。

## 3. 验证结果

- worker 完整构建：103 项，102 通过、1 跳过。
- 新增改名测试：登记与进度事务回滚；登记迁移后恢复；旧名称复用隔离；策略激活与任务标记事务一致；已发布改名幂等重试与后续版本保护。
- 真实重启注入两组：登记完成但未发布；策略已生效但任务待完成。恢复前访问被拒绝，恢复后预编译查询正常脱敏；第二组没有生成重复发布版本。
- 隔离回归：自动血缘与草稿隔离 6 组，事务门禁 3 组，保护边界 6 组，多用户 13 组，中文账号 3 组，审计关联 1 组。另通过旧数据启动后的快照脱敏校验。
- 第一次升级演练因 Proxy 后端连接被拒绝而失败；工具自动恢复旧测试容器和冷备。保留故障现场。第二次升级及后续验证通过；首次连接失败的具体外部原因未定位，不归因于本次代码，也不宣称已修复。

故障注入使用停止 worker 后的隔离冷库；其中策略完成阶段通过恢复已提交任务的待完成状态模拟，不是生产断电实验。

## 4. 绕过网关的同名重建：尚未闭环

已在 Doris 的合成测试库验证 information_schema.metadata_name_ids：改名保持物理 ID，删表后同名、同结构重建的 ID 不同。探针只验证 root 可见性，测试表已清理。

当前代码尚未将此物理标识纳入网关访问和恢复检查。后续需要确认普通账号可见性、初始化旧对象基线、DDL 前后 ID 比较、ID 变化后的阻断与重新确认，且不能在后台扫描时无条件把新 ID 当成旧对象更新。仅依赖名称和字段结构仍不足以证明对象未被替换。
